# Фаза 4 — Задачи

Нарезка спеки (в итерации — дельты) и направления на отдельные тикеты. Человека
о нарезке не спрашивай: тот, кто не пишет код, не может судить о размере задач и
их границах, а вопрос переложит на него твою работу.

Тикеты здесь только создаются и раскладываются так, чтобы каждый выполнялся
отдельно — в своём окне или фоновым агентом, в свой момент.

## Что появляется на диске

```
.orchestrator/
  iterations/iN/tickets/T01.md …   по файлу на тикет
  status.json                      тикеты, требования, инструменты проверки
  runbook.md                       собирает scripts/waves.py
```

## Каждый тикет

- **Вертикальный срез с видимым результатом.** «Форма записи отправляет, и
  письмо приходит» — да. «Настроить сборщик» — нет: это полработы, её нельзя
  проверить.
- **Размер** — одно окно, один чистый контекст, один коммит. В живом прогоне
  хорошо нарезанные тикеты занимали от трёх до двадцати минут; тикет, которому
  нужен час, скорее всего, два тикета.
- **Список файлов**, которые он трогает. По нему скрипт волн решает, какие
  тикеты можно вести одновременно, а окно тикета — что ему можно править.
  Новый файл тоже в списке. Меняет зависимости пакетов — в списке и
  `package.json`, и лок-файл.
- **Зависимости** — номера тикетов, которые должны пройти раньше. Выпуск и
  прочее «после всех» — `"deps": ["*"]`: скрипт сам подставит все тикеты
  итерации, и тикет, добавленный в середине, не проскочит мимо выпуска.
- **Пункты приёмки** — проверяемые строки, каждая отдельным пунктом.
- **Требования, которые он закрывает** — номера из прослеживаемости (ниже).
  Тикет, не закрывающий ни одного требования, лишний.

## Строка приёмки — самое важное место фазы

Она ловит ровно то, что в ней названо. Страница на подменённом шрифте проходит
проверку контраста, пустая страница — проверку переполнения, мёртвая ссылка —
проверку разметки. Поэтому пункт описывает **результат, а не признак**: не «CSS
подключён», а «заголовок нарисован заданной гарнитурой»; не «форма размечена»,
а «заявка дошла».

Проверку всего проекта — тесты, сборку — в пункты не пиши: её проходит каждый
тикет (ниже). В живом прогоне строка «тесты, сборка, офлайн-проверка проходят»
была переписана руками в каждый тикет, в пяти разных формулировках.

## Инструменты проверки

До первого тикета заведи под стек две команды и запиши их в `status.json`:

```json
"tools": {
  "check": "npm run check",
  "shots": "node ~/.claude/skills/son-of-orchestrator/scripts/shots.mjs dist/index.html plan goal action"
}
```

**`check` — одна команда проверки проекта**: тесты, сборка и то, что нужно
именно этому проекту — офлайн-проверка, линтер, проверка типов. Для Node —
скрипт `check` в `package.json`, собирающий остальные через `&&`. Окно тикета
прогоняет её всегда, после своих пунктов. Первый тикет заводит её, если её нет.

**`shots` — снимки экранов** скриптом навыка `scripts/shots.mjs`: адрес или файл
и список экранов, на выходе картинки в `.orchestrator/shots/`. Пункты приёмки
про внешний вид ссылаются на снимки: «на снимке ПЛАНА столбец операций слева».
Нужен Playwright в проекте; нет — поставь его в первом тикете, у которого есть
интерфейс.

## Запись в status.json

```json
{"id": "T33", "iteration": 4, "title": "…", "state": "todo", "attempts": 0,
 "deps": ["T31"], "files": ["src/ai/task.js", "scripts/model-check.mjs"],
 "checks": [{"text": "…", "state": "pending"}]}
```

Номера сквозные по всему проекту: итерация 3 кончилась на T32 — эта начинается с
T33. Команды, коммиты и дашборд ссылаются на номер без итерации.

## Прослеживаемость

Без неё процент попадания на финише посчитать не из чего.

Из расшифровки выпиши **требования** — по одному на каждое высказанное
пожелание, дословно, со ссылкой на номер вопроса. Каждому: пункт спеки, куда оно
легло; тикеты, которые его закрывают; `iteration`; состояние `pending` — на
финише станет `confirmed`, `partial` или `missing`.

Из раздела «что осознанно НЕ делаем» — `out-of-scope`. Они не считаются ни в
выполнении, ни в попадании, но видны: человек должен знать, от чего отказались.

Из раздела дельты «Отменяет» — ссылка у старого требования:
`"superseded_by": "R61"`. Его состояние не меняется: в своей итерации оно было
сделано, и попадание той итерации переписывать нельзя.

Требование без единого тикета — дыра. Либо тикет, либо «не делаем» с причиной:
иначе на финише оно окажется `missing`, и никто не вспомнит почему.

## Волны

Тикеты записаны — собери рунбук:

```
python3 <scripts>/waves.py
```

Скрипт раскладывает тикеты по волнам из зависимостей и показывает ошибки
нарезки: два тикета одной волны на общем файле, цикл, зависимость на
несуществующий тикет. Любая из них — поправь нарезку (добавь зависимость или
слей тикеты) и пересобери, пока их нет. Раздел «Порядок не задан» — пары на
общем файле без зависимости между ними: вместе их не запустят, но кто первый —
случайность; опирается один на правку другого — допиши зависимость.

Рунбук руками не пишется и не правится. В живом прогоне волны и
«что можно одновременно» считались руками, и в зависимостях была ошибка;
скрипт по тем же `deps` и `files` ошибиться не может.

## Порядок

Сначала скелет, на котором всё держится: проект поднимается и открывается. Потом
функции по одной. Потом отделка. Первый тикет заканчивается тем, что запускается,
— иначе проверять следующие не на чем.

Тикеты с интерфейсом ссылаются на нужный кусок направления: решать заново, какого
цвета кнопка, тикет не должен — выйдет пятнадцать разных кнопок.

## Зеркало в GitHub Issues

Есть `gh`, он авторизован и у репозитория есть remote — заведи issue на каждый
тикет и запиши номер в `status.json`. Файлы остаются источником правды, issues —
витрина. Нет чего-то из этого — работай на файлах и скажи одной строкой, без
инструкций по установке: человек не просил заводить GitHub.

## Экран для человека

Один экран простым языком: что даст каждый тикет, без технических деталей и
файлов. Рядом — сколько всего тикетов и что можно начать сразу. Явного одобрения
нарезки не жди.
