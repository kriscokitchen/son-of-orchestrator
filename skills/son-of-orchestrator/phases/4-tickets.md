# Фаза 4 — Задачи

Нарезка `spec.md` и `shape.md` в отдельные тикеты. Человека о нарезке
**не спрашивай** — тот, кто не пишет код, не может судить о размере задач и
границах.

Тикеты не выполняются в этой сессии. Здесь они только создаются и
раскладываются так, чтобы каждый можно было выполнить отдельно, в своём окне,
в свой момент.

## Что появляется на диске

```
.orchestrator/
  tickets/T01.md … T0N.md   по файлу на задачу
  status.json               состояние прогона и прослеживаемость
  runbook.md                готовые строки для запуска, по одной на тикет
  dashboard.html            генерируется скриптом навыка
```

## Каждый тикет

- **Вертикальный срез с видимым результатом.** «Форма записи отправляет и письмо
  приходит» — да. «Настроить сборщик» — нет, это не результат, а полработы.
- **Размер:** одно окно, один чистый контекст, один коммит. Не влезает —
  режь пополам.
- **Список файлов, которые он трогает.** Без него нельзя понять, какие тикеты
  безопасно делать подряд, а какие мешают друг другу.
- **Зависимости** — номера тикетов, которые должны пройти раньше.
- **Пункты приёмки** — проверяемые строки, каждая отдельным пунктом. Не одна
  фраза «работает», а перечень.
- **Требования, которые он закрывает** — идентификаторы из прослеживаемости
  (ниже). Тикет, не закрывающий ни одного требования, лишний.

## Строка приёмки — самое важное место фазы

Она ловит ровно то, что в ней названо, и ничего сверх. Страница на подменённом
шрифте проходит проверку контраста. Пустая страница проходит проверку
переполнения. Мёртвая ссылка проходит проверку разметки.

Поэтому пункт приёмки описывает **результат, а не признак**: не «CSS
подключён», а «заголовок нарисован заданной гарнитурой»; не «форма
размечена», а «заявка дошла».

## Прослеживаемость

Здесь же строится связь между тем, что человек просил, и тем, что будет
сделано. Без неё «процент попадания» на финише посчитать не из чего.

Из `interview.md` выпиши **требования** — по одному на каждое высказанное
пожелание, дословно, с ссылкой на номер вопроса. Каждому требованию проставь:

- пункт спеки, куда оно легло;
- тикеты, которые его закрывают;
- состояние: `pending`, а на финише станет `confirmed`, `partial` или `missing`.

Требования из раздела «что осознанно НЕ делаем» помечай `out-of-scope`. Они не
считаются ни в выполнении, ни в попадании, но показываются отдельно — человек
должен видеть, что именно решили не делать.

**Требование без единого тикета — это дыра, а не мелочь.** Либо заводи тикет,
либо переноси требование в «не делаем» с явной причиной. Молча оставлять нельзя.

## Порядок

Сначала скелет, на котором всё держится: проект поднимается и открывается.
Потом функции по одной. Потом отделка. Первый тикет обязан заканчиваться
чем-то, что запускается.

Тикеты с интерфейсом получают ссылку на нужный кусок `shape.md`. Направление
уже выбрано — тикет не имеет права решать заново, какого цвета кнопка.

## Зеркало в GitHub Issues

Если в системе есть `gh`, он авторизован и у репозитория есть remote — создай
issue на каждый тикет и запиши её номер в `status.json`. Файлы остаются
источником правды, issues — витрина.

Нет `gh`, нет авторизации или нет remote — **это не ошибка.** Работай на файлах
и скажи об этом одной строкой, без инструкций по установке: человек не просил
заводить GitHub.

## Экран для человека

Покажи **один экран простым языком**: что даст каждый тикет, без технических
деталей и без списка файлов. Рядом — сколько всего тикетов и с какого начинать.

Дальше человек запускает тикеты сам. Явного одобрения нарезки не жди.
